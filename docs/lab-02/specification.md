# Lab 2 Sprint Engineering Specification

## 1. Sprint Goal

Deliver a professional, responsive Requester-facing ticketing experience for TokTickIT that lets a
Development Requester create an IT support ticket with attachments, locate it in **My Tickets**
(search, filter, sort, paginate), open a **Ticket Detail** screen, and manage permitted attachments —
all while guaranteeing that one Requester can never view or modify another Requester's ticket.
Authentication is out of scope; a temporary Development Requester selector simulates the logged-in
user for testing purposes only.

## 2. Stakeholder Request Interpretation

IT wants Requesters to be able to self-serve: describe a problem, classify it, attach evidence, submit
it, and later track it. Because real login isn't ready until Lab 3, the sprint needs a safe, obviously
temporary stand-in ("Development Requester Selection") so multi-user ownership can still be tested.
Alongside the functional screens, the sprint must also establish the Zen Green visual language and a
set of reusable UI conventions (forms, badges, lists, loading/empty/error states) that later labs will
build on rather than reinvent.

## 3. Scope

### Included
- Development Requester Selection screen (testing-only identity switch)
- Create Ticket screen (fields, validation, attachment upload, submission)
- My Tickets screen (search, filter, sort, pagination, empty/no-results states)
- Requester Ticket Detail screen (read-only ticket info + attachment management)
- Attachment lifecycle: upload, list, download, soft removal
- Ownership enforcement (backend-level, not just UI hiding)
- Zen Green UI component conventions (forms, badges, tables/cards, states)
- Automated tests: unit, API, UI component, responsive/visual, E2E

### Excluded
- Authentication/security: login, passwords, sessions, tokens, real authorization
- IT Staff dashboard, ticket claiming/reassignment, IT Priority changes
- Public Comments, Internal Notes, Actions Taken
- Ticket status transitions beyond initial `New`
- Administrator functions (managing users, roles, reference data)

## 4. Functional Requirements

- **FR-01** The system shall allow a user to select a Development Requester from a list of active
  Requesters before accessing any ticket screen.
- **FR-02** The system shall persist the selected Development Requester as the current session
  context and allow switching via a "Change Requester" action.
- **FR-03** The system shall allow the current Requester to create a Ticket by supplying Category,
  Related System, Summary, Description, Requested Priority, and optional Attachments.
- **FR-04** The system shall generate a unique, backend-assigned Ticket Number upon successful
  ticket creation and display it to the Requester.
- **FR-05** The system shall allow the current Requester to view a paginated list of only their own
  Tickets in My Tickets.
- **FR-06** The system shall allow the current Requester to search My Tickets by Ticket Number or
  Summary text.
- **FR-07** The system shall allow the current Requester to filter My Tickets by Category, Requested
  Priority, IT Priority, and Current Status.
- **FR-08** The system shall allow the current Requester to sort My Tickets by Created Date, Ticket
  Number, and Last Updated, in ascending or descending order.
- **FR-09** The system shall allow the current Requester to open a Ticket Detail screen for any Ticket
  they own.
- **FR-10** The system shall reject any attempt (UI navigation or direct API call) to view or modify a
  Ticket or Attachment not owned by the current Requester, returning a safe not-found/forbidden
  response.
- **FR-11** The system shall allow the current Requester to add a permitted Attachment to an existing
  Ticket they own, up to the maximum active Attachment count.
- **FR-12** The system shall allow the current Requester to soft-remove an Attachment they own,
  requiring a removal reason, and shall retain the Attachment's metadata without allowing further
  download or preview.
- **FR-13** The system shall show clear loading, empty, no-results, validation-failure, and API-failure
  states on every Requester-facing screen.

## 5. Business Rules

- **BR-01** The official Ticket Number is generated by the backend, is unique, and follows the format
  `TKT-YYYY-NNNNNN` (zero-padded sequence, reset is not required for Lab 2).
- **BR-02** A new Ticket begins with Current Status `New`.
- **BR-03** Lab 2 uses a Development Requester selector instead of login. The selected identity is for
  testing only and is not authentication; no password or session security is implied.
- **BR-04** Only active Development Requesters appear in the selector; inactive Requesters are
  excluded and cannot be used to create or view Tickets.
- **BR-05** A Ticket is owned by exactly one Requester (the Requester selected at creation time); this
  ownership cannot be changed in Lab 2.
- **BR-06** Ticket Number, Ticket Date, Requester, Current Status, Ticket Owner, and IT Priority are
  system-generated or read-only and cannot be edited by the Requester on the Create Ticket screen.
- **BR-07** Ticket Summary is required, trimmed of leading/trailing whitespace, and must be between
  5 and 120 characters.
- **BR-08** Ticket Description is required, trimmed, and must be between 10 and 2000 characters.
- **BR-09** Category and Related System are required and must reference an active, existing record.
- **BR-10** Requested Priority is required and must be one of `LOW`, `MEDIUM`, `HIGH`.
- **BR-11** The Create Ticket form must prevent duplicate submission: the Submit button is disabled
  and shows a busy state while the request is in flight, and a second click before the first response
  returns is ignored client-side.
- **BR-12** If ticket creation fails (validation or server error), all entered field values are preserved
  in the form so the Requester does not need to re-type them.
- **BR-13** Allowed Attachment types are JPG/JPEG, PNG, WEBP, and PDF; any other type is rejected
  before upload with a clear error message.
- **BR-14** Maximum Attachment size is 5 MB per file; oversized files are rejected before upload.
- **BR-15** A Ticket may have at most 5 active (non-removed) Attachments at any time; attempts to
  exceed this are rejected with a clear message.
- **BR-16** Attachment removal is a soft removal: the record and its metadata (filename, size,
  uploader, removal reason, removed timestamp) are retained, but the file becomes non-downloadable
  and non-previewable, and it no longer counts toward the active Attachment limit.
- **BR-17** Removing an Attachment requires the Requester to confirm the action and supply a removal
  reason (required, 3–200 characters).
- **BR-18** Only the owning Requester may add or remove Attachments on their own Tickets; this is
  enforced on the backend regardless of UI state.
- **BR-19** If a Ticket is created successfully but one or more attached files fail to upload, the Ticket
  itself is still saved (Ticket creation and attachment upload are not one atomic transaction); the
  Requester is shown which files failed and may retry adding them from Ticket Detail.
- **BR-20** My Tickets pagination defaults to 10 Tickets per page, with allowed page sizes of 10, 25,
  and 50; an invalid page or page size parameter falls back to the default rather than erroring.
- **BR-21** If no active Development Requesters exist, the Requester Selection screen shows an empty
  state and the rest of the application remains inaccessible.
- **BR-22** If the Development Requester list or ticket data fails to load due to an API/network error,
  the affected screen shows a safe error state with a retry option rather than a blank or broken screen.
- **BR-23** Switching the Development Requester immediately clears any previously loaded
  Requester-specific data (My Tickets, Ticket Detail) and reloads it for the newly selected Requester.
- **BR-24** In Lab 3, the Development Requester selector will be removed and replaced by real
  authentication; the current Requester will then be derived from the authenticated session instead of
  a manual selection, and this data model must not block that transition (e.g., Requester records
  persist independent of the selection mechanism).

## 6. UI Specification Summary

Full detail lives in `ui-spec.md`. Summary:
- **Application shell**: TokTickIT header (Primary green `#006B3C`), My Tickets / Create Ticket nav,
  current Requester name + Change Requester action, active-page indicator, responsive hamburger nav
  below 768px.
- **Development Requester Selection**: centered card, dropdown of active Requesters, explanatory
  "testing only" banner, Continue button, loading/empty/error states.
- **Create Ticket**: system-generated fields visually distinct (read-only shading) from editable
  fields; Summary/Description given full-width, generous space; Attachments section below main
  fields; primary (Submit) and secondary (Cancel) actions at the bottom; inline validation messages
  under each field; success state shows generated Ticket Number.
- **My Tickets**: search bar, filter row (Category, Requested Priority, IT Priority, Current Status),
  sortable columns, paginated table on desktop, stacked cards on mobile, Create Ticket button, Clear
  Filters action, empty/no-results states.
- **Ticket Detail**: read-only ticket info grouped by section, separate Attachments panel with
  active/removed states, Add Attachment control, Back to My Tickets navigation.
- **Badges**: Requested Priority / IT Priority / Current Status use consistent color + text (never
  color alone) per the Zen Green palette.
- **States**: every screen defines loading, empty, no-results, validation-error, and API-failure
  presentations consistent with `ui-spec.md`.

## 7. Data Changes

New/extended Prisma models for Lab 2 (final field-level detail in the Prisma schema):

- **DevRequester** — `id`, `name`, `email` (unique), `isActive`, `createdAt`. Temporary Lab 2 identity
  used in place of authentication; distinct from any future `User`/auth model in Lab 3.
- **Category** — `id`, `name` (unique), `isActive`. Seeded reference table.
- **RelatedSystem** — `id`, `name` (unique), `isActive`. Seeded reference table.
- **Ticket** — `id`, `ticketNumber` (unique, generated), `requesterId` (FK → DevRequester),
  `categoryId` (FK → Category), `relatedSystemId` (FK → RelatedSystem), `summary`, `description`,
  `requestedPriority` (enum: LOW/MEDIUM/HIGH), `itPriority` (nullable, defaulted for Lab 2),
  `currentStatus` (enum, defaults to NEW), `ticketOwnerId` (nullable in Lab 2, reserved for IT Staff
  assignment in later labs), `createdAt`, `updatedAt`.
- **Attachment** — `id`, `ticketId` (FK → Ticket), `fileName`, `storedFileName` (safe/unique on disk),
  `mimeType`, `sizeBytes`, `uploadedAt`, `isRemoved` (boolean, default false), `removedAt` (nullable),
  `removalReason` (nullable), `removedById` (nullable FK → DevRequester).

### Relationships
- One `DevRequester` → many `Ticket` (one-to-many)
- One `Ticket` → one `DevRequester` (many-to-one, required)
- One `Ticket` → many `Attachment` (one-to-many)
- One `Category` → many `Ticket`; one `RelatedSystem` → many `Ticket`

### Indexes / Constraints
- Unique index on `Ticket.ticketNumber`, `DevRequester.email`, `Category.name`, `RelatedSystem.name`
- Foreign key + index on `Ticket.requesterId` (frequently filtered by ownership)
- Composite/secondary indexes on `Ticket.currentStatus`, `Ticket.categoryId`, `Ticket.createdAt` to
  support filter/sort/pagination performance
- `Attachment.isRemoved` indexed to efficiently exclude removed files from active-count checks

**Design decision justification**: `requesterId` is a required, non-nullable foreign key on `Ticket`
(not optional) because BR-05 mandates permanent single ownership at creation; making it required lets
the database itself enforce that no orphan/unowned Ticket can exist, rather than relying purely on
application logic.

## 8. API Contract

Full detail in `api-spec.md`. Endpoints:

| Method | Path | Purpose |
|---|---|---|
| GET | `/api/dev-requesters` | List active Development Requesters |
| GET | `/api/categories` | List active Categories |
| GET | `/api/related-systems` | List active Related Systems |
| POST | `/api/tickets` | Create a Ticket for the selected Requester |
| GET | `/api/tickets` | Paginated, searchable, filterable, sortable list of the Requester's own Tickets |
| GET | `/api/tickets/:id` | Retrieve one owned Ticket (404/403-safe if not owned) |
| POST | `/api/tickets/:id/attachments` | Upload an Attachment to an owned Ticket |
| GET | `/api/tickets/:id/attachments` | List Attachment metadata for an owned Ticket |
| GET | `/api/attachments/:id/download` | Download an active (non-removed) Attachment |
| DELETE | `/api/attachments/:id` | Soft-remove an owned Attachment (requires reason) |

All Ticket/Attachment endpoints require a `requesterId` (query param, header, or session-equivalent
for Lab 2) identifying the current Development Requester, and every ownership check is enforced
server-side.

## 9. Acceptance Criteria

- **AC-01** Given valid Ticket data, when the Requester submits the form, then one Ticket is saved and
  the official Ticket Number is displayed.
- **AC-02** Given no Development Requester is selected, when the user attempts to open My Tickets,
  then the Requester Selection screen is shown.
- **AC-03** Given Requester B is selected, when a Ticket belonging to Requester A is requested, then
  the Ticket data is not returned.
- **AC-04** Given the Summary field is empty, when the Requester submits the Create Ticket form,
  then a field-level validation message appears and no API call is made.
- **AC-05** Given a valid ticket is submitted on a mobile viewport (<768px), when the Requester
  completes the flow, then the confirmation with the official Ticket Number is shown without layout
  breakage.
- **AC-06** Given a file larger than 5 MB is selected, when the Requester attempts to attach it, then
  the file is rejected with a clear message and is not uploaded.
- **AC-07** Given a Ticket already has 5 active Attachments, when the Requester attempts to add a
  6th, then the addition is rejected with a clear message.
- **AC-08** Given an active Attachment, when the Requester removes it with a reason, then it appears
  as removed metadata and its download link is disabled/blocked.
- **AC-09** Given a removed Attachment, when a download is attempted via direct API call, then the
  server rejects the request.
- **AC-10** Given Requester A has 12 Tickets, when My Tickets loads with default pagination, then 10
  Tickets are shown on page 1 with working Next/Previous controls.
- **AC-11** Given a search term matching no Tickets, when the Requester searches, then a no-results
  state is shown (distinct from the empty state for zero Tickets ever created).
- **AC-12** Given the Requester switches from Requester A to Requester B, when My Tickets reloads,
  then only Requester B's Tickets are shown.
- **AC-13** Given the backend is unreachable, when Create Ticket, My Tickets, or Ticket Detail loads,
  then a safe error state with retry is shown instead of a blank/broken page.
- **AC-14** Given the Ticket creation request is in flight, when the Requester clicks Submit again,
  then no duplicate Ticket is created.
- **AC-15** Given an inactive Development Requester, when the Requester Selection screen loads, then
  that Requester does not appear in the dropdown.
- **AC-16** Given a valid Ticket is created but one attachment upload fails, when the response
  returns, then the Ticket is still saved and the Requester is informed which file(s) failed.

## 11. Assumptions and Decisions

- Ticket Number format `TKT-YYYY-NNNNNN` is assumed since the handout shows this style in Figure 1's
  example (`TKT-2025-001234`) but does not mandate an exact format.
- `itPriority` is included in the schema now (nullable/defaulted) even though IT Staff workflow is out
  of scope, because My Tickets and Ticket Detail display it per Figure 1 and BR/AC filtering references
  it; it simply cannot be edited in Lab 2.
- Requester identification for API calls uses a `requesterId` parameter for Lab 2 simplicity, understood
  to be replaced by session-derived identity in Lab 3 (see BR-24).
- Attachment storage location (local disk vs. cloud) is left as an implementation detail in
  `api-spec.md`; either satisfies the soft-removal and access-control rules above.
